# ECF v4.27 — Typed Evidence and Receiver-Side Revalidation

## Purpose

v4.27 implements the first machine-checkable core from the mathematical-foundations document: immutable typed claims, deterministic resource accounting, provenance links, bounded storage, and receiver-side revalidation. It is a narrow engineering milestone, not an AGI system and not a proof of self-created mathematics.

Implementation: `src/flf_ecf/v427.py`.

## Formal state

A receiver ledger is

\[
L_i=(B_i,U_i,M_i,V_i),
\]

where budgets (B_i=(b_c,b_m,b_n,b_e)) bound compute units, memory items, inbound bytes, and energy proxy units; usage (U_i=(u_c,u_m,u_n,u_e)); (M_i) is the immutable-message store; and (V_i) is the receiver's validation ledger.

The invariant is componentwise:

\[
0\le U_i\le B_i,\qquad |M_i|\le b_m.
\]

The implementation's `consume` operation is atomic: either every requested resource is debited or no counter changes. Integer compute and byte counts are deterministic accounting units, not a claim about actual CPU cycles or network-interface bytes. Energy units are software estimates unless replaced by hardware telemetry.

## Typed claim language

The initial allowed claim family is intentionally small:

`distance_threshold_v1`: a relation holds exactly when an observed scalar distance is no greater than a finite non-negative threshold, within a declared scope.

No arbitrary code, executable payload, free-form sender confidence, or sender-issued validation status is accepted as a decision input. Message fields and observations are immutable. Canonical JSON encoding produces a SHA-256 content digest; this detects accidental content changes but is **not** a digital signature, identity proof, or defense against a malicious sender.

## Receiver-side validation protocol

1. Check schema and typed fields at construction.
2. Reject duplicate message IDs and messages exceeding memory or inbound-byte limits without consuming resources.
3. Estimate validation cost using an explicit per-sample policy; atomically debit budget.
4. Store the message as a claim/provenance record.
5. Test the proposed threshold against receiver-local observations only. Sender observations are not counted as receiver validation.
6. Require a configurable minimum sample count. Insufficient samples fail closed.
7. Store the accuracy, local dataset digest, receiver ID, threshold, and finite-test outcome.

A pass means only that the claim passed this receiver's finite test at the configured threshold. It is not a universal proof; data leakage, non-independent samples, adversarial local data, distribution shift, and correlated receivers remain possible.

## Provenance semantics

A message records its origin, monotone-by-convention creation sequence, and parent message IDs. The current module validates uniqueness and prevents direct self-parenting; it does not yet establish global sequence monotonicity, authenticate cell identities, or guarantee a globally acyclic provenance DAG. Those require a network identity/consensus layer and are explicitly out of scope.

## Tests

Run:

```bash
python -m unittest discover -s tests -v
```

The tests cover immutability, deterministic digest, finite-test revalidation, spoofed sender evidence not replacing receiver data, fail-closed minimum sample count, duplicate rejection, atomic resource accounting, memory/byte limits, invalid numeric values, schema rejection, provenance checks, and deterministic validation cost.

## Known limitations / next gate

- Only one claim family is supported.
- Validation accuracy is not calibrated confidence and does not prove truth.
- Caller supplies local observations; independence and sampling protocol are not automatically guaranteed.
- Resource accounting is deterministic bookkeeping, not measured energy/CPU.
- No authenticated identity, signatures, encryption, anti-replay across restarts, durable transactional storage, or concurrent access protection.
- No genome evolution or autonomous hypothesis generation is added here.

Next: connect the v4.26 controlled-exchange experiment to these typed messages and evaluate receiver-side validation under equal budgets, including false claims, correlated evidence, and distribution shift.
