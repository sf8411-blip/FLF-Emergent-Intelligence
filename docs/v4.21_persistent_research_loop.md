# ECF v4.21 — Persistent Research Loop

## Purpose

v4.21 adds a bounded orchestration layer for iterative research. It does not
supply a theorem prover or make a result true by repetition. A caller provides
`step_fn(state) -> StepResult`, which performs one hypothesis/test/counterexample
cycle and returns evidence. The caller may set `success=True` only after its
acceptance checks pass.

## Lifecycle

Statuses are explicit:

- `running`: a research step may be attempted.
- `success`: the caller's acceptance gate explicitly accepted a result.
- `stalled`: the configured number of consecutive non-improving steps was reached.
- `budget_exhausted`: the wall-clock budget for this invocation elapsed.
- `step_limit`: the invocation used its allowed number of iterations.
- `paused`: an external pause callback requested a safe stop.
- `error`: a step failed or returned invalid output.

A non-success terminal state can be checkpointed and resumed. Resume does not
promise progress: the caller should change its search strategy, increase a
budget deliberately, or gather new evidence. A strategy change resets the
stall counter and increments the strategy index, while retaining past evidence.

## Checkpointing

`save_checkpoint` writes JSON to a temporary sibling file, flushes it, then
atomically replaces the target. `load_checkpoint` can enforce a matching
`problem_id` to reduce accidental cross-problem resume. Evidence and metadata
must be JSON-serializable and must not contain NaN or Infinity.

A checkpoint stores orchestration state and recorded evidence, not arbitrary
Python callbacks, open handles, random generator state, external solver state,
or credentials. Those systems must persist their own state separately if exact
reproducibility is required.

## Budgets and scientific safeguards

`LoopConfig` sets maximum steps per invocation, wall-clock seconds, tolerated
non-progress steps, minimum score improvement, and checkpoint frequency. This
is a bounded loop, not a promise of infinite background execution. To continue
long-running work, a scheduler can invoke it again with a saved checkpoint and
a deliberate new budget.

The score is interpreted as lower-is-better; this is a convention, not a
universal objective. `success` is not inferred from a good score: only the
caller can set it after independent validation. The loop records negative
results and errors instead of treating repeated attempts as success. It cannot
guarantee that a problem is solvable or that a caller's acceptance gate is sound.

## Minimal example

```python
from flf_ecf.v421 import ResearchState, StepResult, LoopConfig, run_research

state = ResearchState(problem_id="example-001")

def one_research_step(state):
    # Replace with hypothesis generation, testing, and counterexample search.
    # Set success=True only when independent acceptance criteria pass.
    return StepResult(score=1.0, evidence={"status": "illustration"},
                      note="placeholder; not a scientific result")

state = run_research(
    state, one_research_step,
    config=LoopConfig(max_steps=20, max_seconds=30,
                      max_steps_without_progress=5),
    checkpoint_path="checkpoints/example-001.json",
)
print(state.status)
```

## Acceptance scope

Tests should cover success gating, stall detection, strategy changes, checkpoint
round-trips, problem identity guards, resume behavior, malformed scores, and
iteration limits. Passing these tests demonstrates loop mechanics only; it does
not demonstrate mathematical discovery, autonomous general research, or AGI.
